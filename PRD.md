# Product Requirements Document (PRD)

**Objective:** Provision a private, agile Silicon Mac OS host for deploying AI- and
LLM-based services, driven by Ansible + Homebrew.

## Feature Index

| ID     | Feature                                          | Status |
| ------ | ------------------------------------------------ | ------ |
| F-01   | Colima VM resilience (self-healing LaunchDaemon) | ✅     |
| F-02   | Hermes gateway as a user-scoped host service     | ✅     |

---

## [F-01] Colima VM Resilience

**Goal:** The Colima Docker VM running under `{{ colima_target_user }}` must
survive unclean host shutdowns (reboot, power loss, panic) and return to a
healthy state automatically, without manual intervention and without the
LaunchDaemon crash-looping.

### Background

On 2026-07-07 the host rebooted while the VM was running. On boot the
`com.colima.<user>` LaunchDaemon executed `colima start -f` directly, but the
Lima instance had been left `Broken` — stale `ha.sock`/`ha.pid`/`vz.pid` files
from the pre-reboot process. `colima start` cannot reconcile a Broken instance,
so it exited non-zero; `KeepAlive=true` respawned it immediately, producing a
crash loop (182 restarts) and a 19 MB debug log. Docker was unavailable and the
`hermes-agent` service stayed down until manual recovery. See
`colima-diagnosis.md`.

### Requirements

- **R1 — Self-heal stale state:** startup must clear stale Lima sockets/pids
  (force-stop the Broken instance) before `colima start`, so an unclean shutdown
  recovers automatically.
- **R2 — No crash loop:** a failed start must not tight-loop the daemon; retries
  are throttled and the host stays usable with bounded logs.
- **R3 — Do no harm:** a healthy, running VM must never be stop-started or
  otherwise disturbed by the supervisor.
- **R4 — Boot autostart preserved:** the VM must still start at boot, before
  login, under the system LaunchDaemon.
- **R5 — Idempotent provisioning:** re-running the playbook converges and
  re-bootstraps the daemon only when the supervisor, plist, or profile changes.

### Technical Spec

- `bin/colima-supervisor` — a long-running supervisor loop. Every
  `COLIMA_SUPERVISOR_INTERVAL` seconds (default 30) it checks `colima status`;
  when down it runs `limactl stop -f colima` (clears stale `*.sock`/`*.pid`;
  a no-op when already clean) then `colima start -f`. It never exits, so launchd
  supervises one healthy process instead of respawning a one-shot. (R1, R2, R3)
- `templates/colima-launchd.plist.j2` — `ProgramArguments` invokes
  `{{ colima_supervisor_path }}`; `RunAtLoad=true`, `KeepAlive=true` (restart the
  supervisor if the script itself dies), `ThrottleInterval=30` as a backstop
  against a fast-failing interpreter. (R2, R4)
- `tasks/colima.yml` — installs the supervisor to `{{ colima_supervisor_path }}`
  (`~/.colima/colima-supervisor`, owned by the target user) and re-bootstraps the
  LaunchDaemon when the script/plist/profile change. (R5)

### Acceptance Criteria

- After a hard reboot, `colima status` reports running without manual steps.
- With the instance forced into a Broken state, the supervisor restores it within
  one interval; `launchctl print system/com.colima.<user>` shows no runaway
  `runs` count.
- Starting from a healthy VM, the supervisor performs no stop/start (VM uptime is
  uninterrupted).

## [F-02] Hermes Gateway as a User-Scoped Host Service

**Goal:** The Hermes gateway must run natively on the host as a launchd LaunchAgent
owned by `{{ hermes_target_user }}`, provisioned and converged by Ansible, serving
the same ports off the same data directory as the Docker deployment it replaces —
without the Colima VM in its critical path.

### Background

The gateway ran as a Docker container (`nousresearch/hermes-agent:v2026.8.3`,
`command: gateway run`) defined in `svc/hermes-agent/docker-compose.yaml`. That
deployment had three defects. It was outside Ansible entirely — no task file
referenced `svc/`, `docker compose up -d` was manual, and the `# Generated by
Ansible` headers on `app.env`/`secret.sample.env` described generation that was
never implemented. It depended on the Colima VM, which is what made F-01's
crash-loop take the gateway down with it. And it needed `user: "0"` plus
`HERMES_UID=501`/`HERMES_GID=20` and a writable bind-mount of all of
`/Users/apfelmus` purely so container-written files landed as the right user.

Hermes ships a native macOS install and `apfelmus` already had one
(`~/.hermes/hermes-agent`, git install). Running the gateway directly removes the
VM dependency and the UID/GID mapping.

Hermes must not manage its own launchd service here. `hermes gateway install`
overwrites `ai.hermes.gateway.plist` from a hard-coded template and silently
resets `HERMES_HOME` to `~/.hermes` (upstream #32741); on this host that is a
*different*, older state tree, so the failure would be silent rather than loud.
`refresh_launchd_plist_if_needed()` boots out and re-bootstraps that same label
from inside the gateway's own process group, which can leave the job permanently
unloaded (#43842, #69098). And `hermes gateway start` treats `launchctl bootstrap`
exit 5 as "launchd unsupported" and degrades to an unsupervised detached process
while still reporting the service as loaded (#11323, #42524).

**Accepted trade-off:** inside the container, `terminal.backend: local` meant the
agent's shell commands were confined to the container. On the host the same
setting means unrestricted shell as `apfelmus` — home directory, `~/.ssh`, the
machine itself. This is a deliberate choice, not an oversight; Colima remains
available should the `docker` terminal backend be wanted later.

**The dashboard is dropped.** The container published 9119, but the dashboard was
a separate s6-supervised process inside the image — `gateway run` never started
it, and natively it needs its own `hermes dashboard` process. Upstream describes
it as an optional machine-level management surface; it consumes the gateway's
`/api/status` and nothing consumes it. Verified here: the gateway runs healthy
without it, and the desktop app holds no TCP connections to it. Its `--insecure`
flag is also a no-op since the June 2026 hardening, so a public bind would now
hard-require an auth provider that exists only as env vars. Config editing moves
to the CLI/TUI. Re-adding it later is a second LaunchAgent plus a one-time
`npm run build` in `web/`.

**Colima is out of scope.** It stays, and not only for hermes' sake — the VM also
hosts an unrelated production stack (`ki-nginx`, `wp-kikreativ`, `ki-mariadb`).
This feature removes exactly one container. Note that Colima and Docker state are
per-user: checking them from the `devops` account without `sudo -u apfelmus -H`
reports "colima is not running" even when the VM is healthy
(`colima-diagnosis.md`).

### Requirements

- **R1 — Native host service:** the gateway runs as a LaunchAgent under
  `{{ hermes_target_user }}`, started by launchd at load, with no dependency on
  Colima or Docker.
- **R2 — State continuity:** it serves the existing container data directory
  (`{{ hermes_home }}`) unchanged; no state migration, no divergence onto
  `~/.hermes`.
- **R3 — Parity of exposure:** the API server remains reachable on all interfaces
  on 8642, as the published container port was. The dashboard (9119) is dropped —
  see Background.
- **R4 — Launchd owns supervision:** a crashed gateway is relaunched by launchd
  regardless of exit status, without tight-looping, and never silently downgraded
  to an unsupervised background process.
- **R5 — Exactly one gateway:** no second LaunchAgent may target the same
  `HERMES_HOME`; provisioning retires any hermes-managed agent it finds.
- **R6 — Idempotent provisioning:** re-running the playbook converges and
  re-bootstraps the agent only when the plist changes.
- **R7 — Boot autostart:** the gateway returns after an unattended reboot, with
  nobody at the keyboard.

**R7 depends on host settings outside this repo.** A LaunchAgent has no existence
before login — unlike the Colima LaunchDaemon (F-01 R4), which starts at boot, and
unlike the container's `restart: unless-stopped` that rode on it. R7 holds here
only because the host auto-logs-in: `autoLoginUser = apfelmus` with
`/etc/kcpassword` present, and **FileVault Off** so nothing gates the disk at boot.
Enabling FileVault, or clearing auto-login, silently breaks R7 — the gateway will
sit down until someone logs in. If either must change, this has to become a
LaunchDaemon with `UserName: apfelmus`, mirroring `com.colima.<user>`.

### Technical Spec

- `templates/hermes-gateway.plist.j2` — `ProgramArguments` invokes
  `{{ hermes_bin }} gateway run` in the foreground so launchd supervises the real
  process. `RunAtLoad=true`; `KeepAlive=true` as a plain boolean, not the
  `SuccessfulExit` dict hermes generates — a graceful restart exits 0, which the
  dict form reads as "do not relaunch" (#28135, #4403), and the plain form also
  avoids the `EX_CONFIG (78)` "spawn scheduled" deadlock (#5589).
  `ThrottleInterval=30` bounds restart rate. `EnvironmentVariables` carries `HOME`,
  a `PATH` led by `~/.local/bin`, and `{{ hermes_environment }}`. (R1, R3, R4)
- `default.config.yml` — `hermes_*` vars. `hermes_launchd_label` is
  `de.contentreich.hermes-gateway`, deliberately not `ai.hermes.gateway`, so
  hermes' own plist-refresh path has nothing to claim. `hermes_environment` sets
  `API_SERVER_HOST` and `HERMES_DASHBOARD_HOST` to `0.0.0.0` explicitly: both
  default to loopback natively and only defaulted to all-interfaces inside the
  container. Container-only keys (`HERMES_UID`, `HERMES_GID`) are dropped. (R2, R3)
- `tasks/hermes.yml` — installs Hermes via the official `install.sh` guarded by
  `creates: {{ hermes_bin }}`; never calls `hermes gateway install` or
  `hermes setup`. Boots out and deletes any `ai.hermes.gateway.plist`, mirroring
  how `tasks/colima.yml` retires the brew-services agent. Renders the plist, then
  probes / boots out / bootstraps against `gui/<uid>` gated on
  `hermes_agent_plist.changed`. (R1, R5, R6)

### Acceptance Criteria

- `launchctl print gui/<uid>/de.contentreich.hermes-gateway` reports
  `state = running` with a live pid — not the detached fallback that
  `hermes gateway status` would still call "loaded".
- The API server answers on a non-loopback address, not just `127.0.0.1`, and
  rejects an unauthenticated request with 401.
- The running gateway has `{{ hermes_home }}` open, not `~/.hermes`.
- `kill -9` on the gateway is followed by a launchd relaunch, with `runs`
  incrementing by exactly one.
- After an unattended reboot — nobody at the keyboard — the gateway is running
  again, with exactly one `gateway run` process owned by the target user, and
  `launchctl print-disabled gui/<uid>` does not list the label.
- A second `ansible-playbook main.yml --tags hermes` reports `changed=0 failed=0`
  with bootout/bootstrap skipped and no service bounce.
- Colima is unaffected: `sudo -u apfelmus -H colima status` still reports running,
  `sudo -u apfelmus -H docker ps` still shows `ki-nginx`, `wp-kikreativ` and
  `ki-mariadb` up, and `launchctl print system/com.colima.<user>` shows no new
  `runs`.
- No `hermes-agent` container remains, and the only listener on 8642 is the hermes
  process itself, not the colima ssh port-forward.
